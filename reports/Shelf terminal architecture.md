# Add a remote terminal, not Bash

Shelf should add an optional **remote SSH terminal** to a connected SFTP profile, using a second SSH session channel on the same authenticated connection. This is the right feature because it lets someone inspect and operate the server already open in Shelf without expanding the app into a local command runner. A “Bash terminal” is not cross-platform in the way the question suggests: Linux commonly has Bash, but Windows does not ship Bash as its system shell, and Git Bash, WSL, MSYS2, and Cygwin are separate optional environments. The terminal screen can look and behave consistently on Windows and Linux, but the program behind a local terminal differs by operating system. Shelf’s current Rust backend already uses `russh` for SSH and `russh-sftp` for SFTP, so a remote shell is a focused extension of the present trust, authentication, and connection model. The first release should keep transfers primary and put one collapsible “Remote terminal” drawer beneath the two file panes. A local terminal can be reconsidered later as a separate, explicitly approved feature with a separate security model.

## Bash is portable language, not portable shell installation

**Bash is not the Windows default shell.** A cross-platform terminal UI is practical because terminals exchange UTF-8 text and virtual-terminal control sequences; Windows ConPTY specifically transports UTF-8 text mixed with VT sequences, while Linux PTYs provide the same kind of terminal relationship to a child process. But the shell process differs. The cross-platform Rust PTY library `portable-pty` resolves the Unix default from `$SHELL`, the password database, then `/bin/sh`; on Windows it resolves `ComSpec` and otherwise uses `cmd.exe`. That is strong evidence that a product should describe a local terminal as a **native-shell terminal**, not promise Bash everywhere. ([portable-pty source](https://docs.rs/portable-pty/latest/src/portable_pty/cmdbuilder.rs.html)) ([Microsoft ConPTY documentation](https://learn.microsoft.com/en-us/windows/console/createpseudoconsole)) ([Linux pty(7)](https://man7.org/linux/man-pages/man7/pty.7.html))

If Shelf later needs a local terminal, it should default to Command Prompt or a selected PowerShell/Pwsh profile on Windows, and the login shell on Linux. Bash on Windows should be an explicit detected profile only: for example a particular Git Bash executable or a selected WSL distribution. Each needs its own executable path, arguments, working-directory rules, and tests. `portable-pty` supports a separately supplied program, arguments, and working directory, so Shelf would not need to build a shell-command string or route user input through `cmd.exe /c`. ([CommandBuilder API](https://docs.rs/portable-pty/latest/portable_pty/cmdbuilder/struct.CommandBuilder.html))

That distinction matters more than terminology. A local shell runs with the desktop user’s files, credentials, network identity, and process privileges. A remote shell runs commands on the already connected server, under the already authenticated SSH identity. The latter fits Shelf’s purpose; the former materially expands it.

## SSH already separates file transfer from shell access

**SFTP and an interactive shell are different SSH session uses.** SSH defines a session channel as a vehicle for a remote shell, command, application, or subsystem. An SFTP channel is committed to the `sftp` subsystem and cannot later become a shell: only one shell, command, or subsystem request can succeed on that channel. SSH also allows multiple channels over one authenticated connection, so Shelf should leave the current SFTP channel in place and create a second `session` channel for the terminal. ([RFC 4254, sessions](https://datatracker.ietf.org/doc/html/rfc4254#section-6)) ([RFC 4254, channels](https://datatracker.ietf.org/doc/html/rfc4254#section-5))

Opening that terminal channel requires a `pty-req` with terminal type and dimensions, followed by a `shell` request. Resizing the drawer must propagate a `window-change` request. `russh` exposes the needed client operations: open a session channel, request a PTY and shell, write data, receive channel messages, resize, send EOF, and close. ([RFC 4254, PTY request](https://datatracker.ietf.org/doc/html/rfc4254#section-6.2)) ([RFC 4254, window change](https://datatracker.ietf.org/doc/html/rfc4254#section-6.7)) ([russh Channel API](https://docs.rs/russh/0.63.3/russh/struct.Channel.html))

This does not guarantee a terminal on every server. Server policy can deny PTYs, force a command, or set `MaxSessions` to one; OpenSSH documents a default `MaxSessions` of 10 and notes that one effectively turns off session multiplexing. The first release should show a clear “server does not allow an interactive terminal” state and keep SFTP usable if terminal setup fails. It should not silently create a second SSH connection unless the product explicitly adopts and documents that fallback, because it changes authentication, server-side auditing, and resource use. ([OpenSSH sshd_config PermitTTY](https://man.openbsd.org/sshd_config#PermitTTY)) ([OpenSSH sshd_config MaxSessions](https://man.openbsd.org/sshd_config#MaxSessions))

## Shelf needs one small connection-state refactor

Shelf currently stores only `Option<SftpSession>` behind one Tokio mutex. During `connect_sftp`, it authenticates a `russh::client::Handle`, opens the SFTP channel, turns it into an `SftpSession`, and then drops the handle. That means the running application has no retained SSH object through which it can open a later terminal channel. `russh` documents the handle returned by `connect` as the object used to create channels, so the core implementation change is to retain it alongside the SFTP session and connection identity. ([russh client source](https://docs.rs/russh/0.63.3/src/russh/client/mod.rs.html#299-304))

The resulting state should be a connection owner containing the authenticated handle, the SFTP session, a connection generation, and at most one terminal-session record. Opening the drawer briefly locks only the connection owner, creates a second SSH channel, requests `xterm-256color` with the measured columns and rows, and starts the shell. Reader and writer tasks then own terminal I/O so they do not keep the shared connection-state mutex across output streaming or user typing. This is important because Shelf’s present remote listing and transfer commands retain the SFTP mutex while their asynchronous work runs; applying that pattern to terminal traffic would make an active upload or download delay the terminal.

The resolved project dependency is already `russh` 0.63.x, and the referenced client-side PTY panic affecting versions through 0.62.2 was fixed in 0.62.5. That removes one known adoption blocker, but does not replace a prototype against Shelf’s target servers. ([russh security advisory](https://github.com/Eugeny/russh/security/advisories/GHSA-cqjc-rmpq-xprq))

## xterm.js fits a narrow remote terminal drawer

Use **`@xterm/xterm` with `@xterm/addon-fit`** in the React/Tauri frontend. xterm.js is a browser terminal emulator, not an SSH client or shell, which cleanly leaves SSH authentication and channel control in Shelf’s Rust backend. The Fit add-on measures the drawer and supplies the rows and columns needed by the SSH PTY; xterm.js also provides terminal resizing, configurable scrollback, selection, contrast, and screen-reader support. Start with its DOM renderer for the broadest assistive-technology path, and treat WebGL as a later opt-in performance enhancement. ([xterm.js add-ons](https://xtermjs.org/docs/guides/using-addons/)) ([xterm.js terminal options](https://xtermjs.org/docs/api/terminal/interfaces/iterminaloptions/))

The UI should be a single collapsed-by-default bottom drawer associated with the active connected profile. Its header should name `user@host:port`, show `Connected`, `Disconnected`, or `Shell exited`, and provide clear, copy, and close controls. Do not add terminal tabs, port forwarding, local-shell modes, a serial console, a command library, or saved transcripts. On terminal focus, pass Ctrl+C, Ctrl+Z, arrows, Tab, and other terminal keys to the remote host; normal Shelf shortcuts remain active only outside the terminal. Paste must be user initiated and should confirm multiline content. Terminal output must be rendered only by the emulator, never inserted as HTML.

The frontend should send keyboard data unchanged and debounce resize messages. The backend should stream ordered terminal output through a Tauri `Channel`, not events: Tauri documents channels as its fast ordered stream mechanism, while events use JSON and rapid asynchronous listeners can observe out-of-order data. xterm.js buffers asynchronous writes and documents that fast output can make it unresponsive without flow control, so the implementation needs bounded backend queues, a scrollback cap, and load testing before adding more features. ([Tauri frontend communication](https://v2.tauri.app/develop/calling-frontend/)) ([Tauri Rust commands and channels](https://v2.tauri.app/develop/calling-rust/)) ([xterm.js flow control](https://xtermjs.org/docs/guides/flowcontrol/))

## Security and delivery should stay deliberately narrow

The remote terminal is a privileged remote-control surface, even though it avoids local code execution. It must require an explicit Open remote terminal action after a connection is established; it must never auto-start a shell or expose arbitrary Rust command execution. Keep IPC to `open_terminal`, `write_terminal`, `resize_terminal`, and `close_terminal`, scoped to an opaque terminal ID and active connection generation. Reject stale IDs, writes before readiness, writes after close, and oversized messages in Rust. Tauri identifies frontend-to-core IPC as a trust boundary and recommends restrictive capabilities and CSP; only the required terminal commands belong in Shelf’s main-window capability. ([Tauri security](https://v2.tauri.app/security/)) ([Tauri capabilities](https://tauri.app/security/capabilities/)) ([Tauri CSP guidance](https://v2.tauri.app/security/csp/))

Host verification needs tightening before shipping shell access. Shelf’s present `trust_new_host` boolean writes an unknown key immediately. The terminal release should show the server SHA-256 fingerprint and require explicit first-use confirmation, then reject changed keys until the user deliberately reviews and replaces the saved entry. OpenSSH frames strict host-key checking as protection against man-in-the-middle attacks and never automatically accepts changed keys in strict mode. Do not log keyboard input, passwords, terminal output, or command history. ([OpenSSH ssh_config StrictHostKeyChecking](https://man.openbsd.org/ssh_config#StrictHostKeyChecking))

Stage one is a compile-tested backend spike: retain the `russh::client::Handle`, open a second session channel, request PTY and shell, relay output through a bounded channel, and prove SFTP listing continues while the shell runs. Stage two is the xterm.js drawer with fit/resize, focus handling, copy/paste safeguards, and visible lifecycle errors. Stage three hardens host-key confirmation, connection-generation checks, queue and scrollback limits, CSP/capabilities, and terminal shutdown. Stage four validates on supported Windows and Linux desktop builds against a controlled SSH server, including `printf`, Unicode, invalid byte sequences, `stty size`, Ctrl+C of a long command, EOF/close, PTY rejection, changed host keys, `MaxSessions 1`, reconnect with stale IDs, and sustained transfer plus high terminal output. A successful frontend build alone is not sufficient evidence; the interaction requires real SSH-server tests.

## Conclusion

Shelf does not lack a terminal because it needs Bash; it lacks one because SFTP alone does not provide a shell channel or a terminal renderer. The clean upgrade is a **single remote SSH terminal drawer** built on a second channel of the existing authenticated connection. It is cross-platform for Shelf’s Windows and Linux desktop users because the desktop app renders terminal bytes and the remote server supplies the shell. That preserves Shelf’s focused SFTP identity while giving users the exact practical escape hatch they expect: inspect the remote machine and run a command without leaving the transfer workflow.

If a local terminal remains desirable after this release, make it a separate product decision. Implement it with native shells by default and optional, explicitly configured Bash providers on Windows; do not present it as one universal Bash feature.
